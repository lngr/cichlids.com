# Architecture Decision Records (ADRs)

This area collects the project's **Architecture Decision Records (ADRs)**.
An ADR captures exactly **one** significant decision — with context, considered
options, rationale, and consequences.

## Why ADRs

Decisions should be **traceable and durable** — independent of people, tickets, or
temporary documentation. ADRs are the long-lived decision layer of the project.

## Conventions

> **Binding rules**
> - **Self-contained:** Each ADR stands **on its own** and remains understandable even
>   if other project documents disappear. ADRs reference **only** other ADRs, not other
>   repo files.
> - **One decision per ADR.**
> - **Immutable once `Accepted`:** A decision that has been made is not rewritten. If it
>   changes, a **new** ADR is created that *supersedes* the old one (the old one gets
>   status `Superseded by ADR-NNNN`).
> - **Language:** English. **Format:** plain Markdown, MADR-oriented.

**File naming:** `NNNN-kebab-title.md` (consecutive four-digit number).

## Status workflow

| Status | Meaning |
|---|---|
| `Proposed` | Proposed, not yet decided. |
| `Accepted` | Decided and in effect. |
| `Deprecated` | No longer recommended, but not (yet) replaced. |
| `Superseded by ADR-NNNN` | Replaced by a newer ADR. |
